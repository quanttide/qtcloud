# Studio 原型 v3 设计

一句话：v3 把「正在编写的方案」放上屏幕正中，让流程自己往下流——**人只在需要拍板的地方出现**。

## 要解决的问题：人肉路由器

这个问题不是猜的，来自 2026-09-07 的业务日记（「河床」）：

> 一个学员的旅程横跨约十个系统，每个衔接点都是「人肉路由器」；状态机的迁移全靠人肉对账伪造。之前一切自动化收效甚微，是因为在给一条断河修闸门；真正该做的是把河修连续。

量潮自己的流程就是这个病：每个环节内部早已自动化，真正吃人的是**环节之间的衔接**——靠人把状态搬来搬去。所以工作台的第一职责是**把河修连续**：任务自动往下流，人只在闸门（验收）出现。

检验标准一句话：**除了拍板，还有哪一步需要人搬？答案应该是「没有」。**

## 打开 v3 你会看到什么

拿量潮数据的真实业务当例子——高校数据治理项目的方案编写。按一次完整的使用过程讲：

1. 左边大半屏是《A 校数据治理项目方案》正文（分「背景与目标 / 数据范围 / 处理流程 / 报价 / 交付计划」五节，右上角当前版本 v1）。右边窄栏是任务列表，第一条「数据可行性评估 · 数据云」正在干。
2. 几秒后数据云交付——左边「处理流程」一节出现修改对照：红字删除线是原文，绿字是提议的新文字（比如把「按月清洗」改成「按周清洗」，附理由）。
3. 你读完修改，点「通过」。绿字并入正文，版本号跳成 v2，方案下方多一行记录：「v2 · 数据可行性评估 · 数据云」。
4. **接下来你什么都没做**：「报价核算（执行云）」自动就绪、自动开工——上游验收通过，河自己往下流，没有人去派单。等它交付，你又出现拍板。
5. 最后一项「方案定稿检查」是你自己的任务，做完提交、验收，顶部出现一行字：方案定稿。

整个旅程你只出现了两次，都在闸门上。其余衔接是自动的——每次自动衔接，界面都会标注「自动衔接」，指认**这里原来需要一个「人肉路由器」**。

## 验收的两种结果

- **通过**：修改进正文，版本号加一。
- **驳回**：必须写一条意见（比如「交付周期写死 30 天太激进，客户数据源每月才更新」），任务退回给干活的那朵云，方案一个字不动。

## 右侧任务栏

从上到下三段，一眼扫完：

- **等你拍板**（黄色）：有修改等你判定。点任务，左边方案跳到对应章节。
- **正在干**（蓝色）：哪朵云在干哪件事，干完自动交修改。
- **可以开始**：就绪的任务里，**云的自动开工，人的等人来做**。还没轮到的显示「在等谁」。

## 派活：说话就行

顶部一句话输入框。demo 预置了几个听得懂的意图（比如「增加客户确认环节」），听到就拆成任务；听不懂就直说「这句我还不会拆」，不会偷偷塞一个假任务。

## 哪些是真的，哪些是演的

- **真**：方案正文、修改内容、版本记录、状态流转规则（上游验收 → 就绪 → 云自动开工）。验收通过后方案真的变了，刷新也不丢。
- **演**：每朵云交回什么修改是预排的；几秒的延迟只是为了有「在干活」的感觉。
- **没做**：真的 AI 拆解、真的云接入、多人协作。

## 给实现者

- 状态由规则推进：上游全部验收 → 就绪；就绪的云任务**自动开工**、交付后自动进入待验收；人的任务等人操作。人不搬运任何状态。
- 类型沿用 v3：`Document`（方案本体，含版本）、`Change`（一条修改：章节、原文、新文字）、任务新增 `output: Change[]`。
- 自动衔接处标注「自动衔接 · 原为人工搬运」。
- 评判原则见仓库根 `AGENTS.md`（第一原则：连续优先于完备）。

## 做完怎么算合格

1. 不看任何说明，打开 5 秒内知道现在该自己干什么。
2. 每次验收都看着章节的修改对照拍板，不是看一行摘要。
3. 驳回之后，方案一个字都没变。
4. 遮住右边任务栏，左边仍是一份能独立读的方案。
5. 数一数人出现的次数：除了拍板和自己领的任务，旅程中没有任何一步需要人搬；每个自动衔接处，界面都指认了「这里原来靠人」。
6. 按 AGENTS.md 自评分，目标 5 分以上，且走查缺陷清零。
